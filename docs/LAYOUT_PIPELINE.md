# Этапы построения Blueprint-графа

Построение графа разделено на три явных этапа; каждый этап — отдельный инструмент со своим
входом и выходом, поэтому их можно применять по отдельности и сверять результат между собой.
На первом этапе координаты не относятся к смыслу графа.

**Рабочий цикл = ступени 1 и 2.** Ступень 3 (декоратор) помечена «в разработке» (2026-09-28):
`src/decorator.js` и `tools/check-decoration.mjs` остаются в репозитории, но в цикл не входят —
`positionBlueprint()` decorate не вызывает, фикстура ступени 3 не коммитится, а в `npm test`
проверяются только ступени 1–2. Вернуть decor-ступень в цикл = снять пометки и вернуть
`--stage 3` в `package.json` (плюс `check-decoration.mjs`).

| Ступень | Инструмент | Вход | Выход |
|---|---|---|---|
| 1 — генератор нод | `src/stage1.js` (`tools/gen-three-stage-test.mjs --stage 1`) | спека: ноды, соединения пинов, марки `@row/@col` | только код нод: без координат, проводов, knot'ов и комментов |
| 2 — расстановщик | `src/arranger.js` | код ступени 1 + заложенные марки и соединения | провода, координаты черновика, стадиумы из 4 knot'ов (пары по строкам пинов) на каждом несоосном exec-проводе |
| 3 — декоратор ⚠ WIP | `src/decorator.js` | код ступени 2 | (вне цикла) плоские ряды (одинаковый Y exec-нод), столбец детей форка, зазор 5 клеток по X, переносы-стадиумы по пинам |

Ступени передают друг другу ТЕКСТ (`Begin Object … End Object`): расстановщик и декоратор
парсят вход, меняют координаты (и, если нужно, `LinkedTo` при создании knot-переносов) и
сериализуют обратно. Остальной код ноды остаётся дословным — см. `generateUEText(nodes, { syncLinks: true })`.

## 1. Генератор нод — `src/stage1.js` (над `src/creator.js`)

`src/creator.js` создаёт существующие типы UE-нод, пины, значения по умолчанию и двусторонние
связи. `linkPins()` только записывает концы связи и не перемещает ноды. У фабрик пока сохранён
необязательный параметр стартовой позиции для совместимости; при новом сценарии считай его
временным до второго этапа.

`createStage1Graph(specText, { registry })` — ступень 1 целиком: разбор спеки, фабрики нод,
разрешение соединений и марок (в код они НЕ пишутся) и самопроверки. Спека (один узел на
строку; формат `tools/make-node.mjs`):

```graph
set nameBase 1000          # (опц.) имя узла = <Класс>_(nameBase + номер) — трассировка «узел 7»
1 event InitOverlapHook                 @row=0 @col=0
2 bind Actor.OnActorBeginOverlap        @row=0 @col=1
link 1.then 2.execute
```

Генератор отвечает за корректность: класс, количество, пины (входы/выходы), точные имена и
типы, значения по умолчанию, уникальные `PinId` (без них ступени 2 не за что зацепить провод).
`@row`/`@col` обязательны — без них узел не создаётся (никаких «угадываний» координат);
дробный `@row` (2.5) = подстрока того же уровня. Каждый `link` разрешается в конкретные пины
и проверяется, но остаётся **закладкой** (`connections` в результате функции) — провод пишет
расстановщик через `applyConnections(nodes, connections)`. Сам генератор ноды не двигает
(`NodePosX/NodePosY = 0`) и не соединяет (ни одного `LinkedTo`); knot'ы, комментарии и
выравнивание пинов — не его задача. `verifyStage1()` сверяет текст с моделью (ноды, пины,
нулевые координаты, отсутствие связей) и ловит потерю кода при сериализации.
Эталонный тест с критериями: `tests/three-stage-01.sequence.md`.

## 2. Расстановщик — `src/arranger.js`

`arrangeRows(rows, { x, y, gap, rowGap })` размещает переданные явно ряды: внутри ряда слева направо, каждый следующий ряд ниже предыдущего. Интервал учитывает оценочную ширину ноды и `gap`. `arrangeFlow()` может вывести простой порядок из связей, но для ветвлений, data-only узлов и случаев, где порядок задаётся exec-цепочкой, передавай ряды явно.

Этот этап отвечает за базовую структуру, последовательность и материализацию соединений ступени 1 (`applyConnections(nodes, connections)`; генератор `LinkedTo` не пишет). Результат: расставленные ноды, созданные knot-ноды и `levels` (границы рядов `top/bottom`). Шаг сетки — `GRID` = 16px.

### Потоковая раскладка — `src/flow-layout.js` (калибровка ступени 2)

`arrangeExecFlow(nodes, options)` раскладывает exec-хребет и столбцы побочных выходов, выравнивает
exec-пины, размещает чистые деревья слева/снизу или сверху и дублирует Get/Self у каждого потребителя.
Пока это отдельный режим; `positionBlueprint()` без явных рядов по-прежнему вызывает `arrangeFlow()`.

**Правило 13 (пользователь, 2026-10-02):** каждый дополнительный слой exec-выходов увеличивает
расстояние до левой стенки следующих нод на 8 шагов сетки (128 px). `flowExecGap(node, gap, execLayerGap)`
считает `gap + max(0, N − 1) × execLayerGap`, где N — число видимых exec-выходов, включая неподключённые;
скрытые/свёрнутые advanced, входы, данные и делегаты не считаются. В `arrangeExecFlow` по умолчанию
`gap = 48`, `execLayerGap = 8 * GRID`. После ширины источника добавляется этот зазор, затем X привязывается
вверх к сетке 16. Все первые потребители стоят у общей стенки: прибавка не накапливается по строкам
столбца и не переносится на обычные одновыходные продолжения. `execLayerGap: 0` отключает только прибавку.

Высокая предыдущая нода задаёт нижнюю границу для чистого дерева; сама по себе её высота не должна
вытеснять дерево наверх. В боковом ряду fork-источник считается предыдущей нодой для выравнивания значений.
См. координаты, новый verdict и границы подтверждения в
[`flow-demo-2-reference.md`](../sweep/copyback/flow-demo-2-reference.md). Расширение зазора и эти привязки
не создают knot'ы и не меняют связи (кроме уже существующего правила копий Get/Self).

### Knot'ы — только перенос назад (правила пользователя 2026-10-01)

Knot'ы создаются **только** для exec-провода, у которого вход цели левее выхода источника (перенос назад,
как в референсах). Все остальные exec-провода — прямое соединение нод, даже если пины на разной высоте
(косой провод правится при ручной доводке). Перенос — всегда ровно **4** knot'а, слияния нет:

```text
выход A ── K1
           │           (спуск из пина в щель)
           K2 ─────────────── K3      ← линия щели
                              │       (вертикаль в свободной колонке)
                              K4 ── вход B
```

* K1 = (X пина-выхода A, Y пина-выхода A) — у самого пина;
* K2 = (тот же X, **линия щели**) — прямо под K1. Линия щели = центр между низом A и верхом B, привязанный к
  сетке 16px, но не выше низа A; если B выше A (щели снизу нет) — на 2 шага сетки ниже низа A;
* K3 = (X колонки, линия щели);
* K4 = (X колонки, Y пина-входа B) — дальше провод горизонтально входит в B.

Колонку вертикали подбирает `transferColumnX(...)`: засевки «у пина-входа цели (−2·W)» → «у пина-выхода
источника» → «левый внешний край графа» → «правый внешний край», от каждой шаг ±W. Колонка свободна, если
knot'ы K3/K4 не попадают в прямоугольник ни одной ноды (включая источник и цель), вертикаль K3→K4 не
перечёркивает чужие ноды на своём диапазоне Y и knot'ы не слипаются. Ноды не двигаются.

Правило проверяет `node tools/check-knot-corridor.mjs` (входит в `npm test`): ровно 4 knot'а, K1 на
пине-выходе, K2 под K1 не выше низа источника, K2·K3 на одной линии щели, K3·K4 в одной колонке, K4 на
строке входа, вертикаль в свободной колонке, ни один knot не внутри ноды. Рамки комментариев проверка
пока считает нодами (известное ложное срабатывание на демо с комментами).

История (снятые правила): «стадиум на каждый несоосный провод» (2026-09-28), «K1·K2 на строке выхода»,
слияние knot'ов ближе 3/7 шагов и «нет knot'ов ближе 20 шагов» — все заменены правилом выше (журнал —
`docs/ENGINE_VERIFIED.md`).

## 3. Декоратор — `src/decorator.js` ⚠ в разработке, вне основного цикла

Ступень 3 доводит черновик ступени 2 и меняет **только координаты**: ни создания/удаления нод,
ни правки пинов и `LinkedTo`, ни переноса нод между уровнями. Правила — из формулировки
пользователя (2026-09-27). С 2026-09-28 этап приостановлен по решению пользователя: модуль и
его проверки (`tools/check-decoration.mjs`) сохранены, но конвейер его не вызывает —
ниже он описан как справка, что делать при возврате.

| Проход | Что делает |
|---|---|
| `flatLinks()` | раскрывает цепочки knot'ов: связи становятся «нода → нода» с `via`; переносы для декоратора — способ прокладки, а не узлы, которые надо «выровнять» |
| 1 — плоские ряды | ряд = лента: все его ноды получают `y = Y ряда` (лесенка запрещена), следующий узел = `max(курсор ряда, правый край водителя) + clearance`. `clearance = 5 * grid` (80) — «5 шагов сетки по X» |
| 1 — столбец форка | у узла больше одного использованного exec-выхода → дети получают общий `X = правый край родителя + clearance`; ребёнок в другом уровне сохраняет Y своего уровня (иначе ряд перётек бы). Внутри одного ряда столбец «друг под другом» невозможен, когда высота ноды больше шага пинов (32px) — дети того же ряда остаются лентой, а настоящий столбец задаётся маркой уровня (`@row=0.5`), как `4`/`5` в эталонном тесте |
| 2 — данные | двигаются только «чистые» ноды данных (без exec-пинов). Соседу по ряду — пин в пин + зазор; узлу из другого ряда — строго под пин входа (`X` правого края = `X` пина-входа), провод вертикальный. Лестница вариантов: Y+X → X → Y → оставить, причина в `notes` (печатается в `--report`) |
| 3 — щели уровней | если выравнивание съело межуровневую щель, ряд (и всё под ним) сдвигается вниз на `minLevelGap = 2 * grid`; состав и порядок уровней не меняются |
| 4 — переносы | `transferRoute` по пинам концов на ГРАНИЦАХ уровней после выравнивания: пары knot'ов выровнены по Y (K1·K2 — строка пина-выхода, K3·K4 — строка пина-входа), между ними соосная вертикаль в свободной колонке. Совместимость: если в `via` ровно 2 knot'а (старая механика), они ставятся на коридорный Y (`execCorridorY`) по пинам концов |

Привязка к сетке по умолчанию выключена (`snap: false`): округление разбирает ровно то, ради чего
ступень существует — соосность пина и knot'а. Модель пина (`pinCenterY`/`estNodeWidth`) общая со
ступенями 1—2, её калибруют замерами из Unreal Editor (можно передать свою `pinY(node, pin)`).

Критерии закреплены тестом `node tools/check-decoration.mjs [вход] [выход] [зазор]` (запускается
вручную после `npm run stages:wip` — в `npm test` не входит, пока ступень отложена): A — Y exec-нод одного ряда идентичен, B — дети форка в столбце, C — зазор 5 клеток,
D — стадиум соосен пинам и выровнен парами по Y (для межуровневой связи вертикаль стоит в
свободной колонке, для связи внутри ряда knot'ы умещаются в щель между нодами), E — наложений нет,
F — состав уровней, их верх и код нод не тронуты.

## Объединённый вызов

`src/layout-pipeline.js` экспортирует `positionBlueprint()` — вызов расстановщика (ступень 2).
Декоратор к нему не подключён: чтобы получить ступень 3, передай опцию `decorate` —
`positionBlueprint(nodes, { rows, arrange, decorate: { clearance: 80 } })`; она же включает
возврат `decorated: true`. Создание нод и связей выполняется заранее.

### Два layout-стека: какой где работает

В репозитории исторически два механизма раскладки, и оба живые:

| стек | где код | кто им пользуется | что умеет |
|---|---|---|---|
| **ступенчатый (основной цикл)** | `src/stage1.js`/`src/creator.js` → `src/arranger.js` (+ отложенный `src/decorator.js`), точка входа `positionBlueprint()` | `tools/gen-three-stage-test.mjs`, `tools/check-decoration.mjs`, `tools/check-knot-corridor.mjs`, пробы `gen-pipeline-smoke.mjs`/`gen-dispatcher-bound.mjs` | марки рядов (`@row=0.5`), столбцы детей форка, стадиумы из 4 knot'ов с парным Y и свободными колонками вертикалей, контроль наложений; раскладка отделена от создания нод |
| **legacy** | `layoutRow`/`layoutRows`/`layoutDecorated`/`decorateExec` + `estNodeWidth`/`pinCenterY` в `src/generator.js` | `tools/make-node.mjs` и его фикстуры (`sweep/27b`, `30`, `32`), `tools/gen-sweep.mjs`, `gen-subset`, `gen-r21b/r25/r26`, часть asserts в `tests/` | ряд/сетка по одной строке, `--wrap`, `--decorate` — «упаковка» без рядовых марок и без отдельной ступени декора |

Решение (2026-09-28): оставить оба. Legacy не «дублирует» расстановщик — он обслуживает CLI
`make-node` и категориальный корпус sweep, geometry-ожидания которых зафиксированы тестами и
подтверждены движком; удалить его означало бы переписать ~40 проверок и разморозить VERIFIED
фикстуры. Новый код (генератор → расстановщик → декоратор) пишется только поверх
`positionBlueprint()`; функции из `generator.js` для новых генераторов — не путь развития.

STRICT и unit-тесты проверяют структуру и расчёты модели, но не подтверждают UE-вставку, компиляцию или фактическое расположение пинов в редакторе.
