# Этапы построения Blueprint-графа

Построение графа разделено на три явных этапа; каждый этап — отдельный инструмент со своим
входом и выходом, поэтому их можно применять по отдельности и сверять результат между собой.
На первом этапе координаты не относятся к смыслу графа.

| Ступень | Инструмент | Вход | Выход |
|---|---|---|---|
| 1 — генератор нод | `src/stage1.js` (`tools/gen-three-stage-test.mjs --stage 1`) | спека: ноды, соединения пинов, марки `@row/@col` | только код нод: без координат, проводов, knot'ов и комментов |
| 2 — расстановщик | `src/arranger.js` | код ступени 1 + заложенные марки и соединения | провода, координаты черновика, knot-переносы |
| 3 — декоратор | `src/decorator.js` | код ступени 2 | координаты по пинам: Y пин-в-пин, зазор 5 клеток по X, knot'ы по пинам в коридоре |

Ступени передают друг другу ТЕКСТ (`Begin Object … End Object`): расстановщик и декоратор
парсят вход, меняют координаты (и, если нужно, `LinkedTo` при создании knot-переносов) и
сериализуют обратно. Остальной код ноды остаётся дословным — см. `generateUEText(nodes, { syncLinks: true })`.

## 1. Генератор нод — `src/stage1.js` (над `src/creator.js`)

`src/creator.js` создаёт существующие типы UE-нод, пины, значения по умолчанию и двусторонние
связи. `linkPins()` только записывает концы связи и не перемещает ноды. У фабрик пока сохранён
необязательный параметр стартовой позиции для совместимости; при новом сценарии считай его
временным до второго этапа.

`createStage1Graph(specText, { registry })` — ступень 1 целиком: разбор спеки, фабрики нод,
разрешение соединений и марок (в код они НЕ пишутся) и самопроверки. Спека (один узел на
строку; формат `tools/make-node.mjs`):

```graph
set nameBase 1000          # (опц.) имя узла = <Класс>_(nameBase + номер) — трассировка «узел 7»
1 event InitOverlapHook                 @row=0 @col=0
2 bind Actor.OnActorBeginOverlap        @row=0 @col=1
link 1.then 2.execute
```

Генератор отвечает за корректность: класс, количество, пины (входы/выходы), точные имена и
типы, значения по умолчанию, уникальные `PinId` (без них ступени 2 не за что зацепить провод).
`@row`/`@col` обязательны — без них узел не создаётся (никаких «угадываний» координат);
дробный `@row` (2.5) = подстрока того же уровня. Каждый `link` разрешается в конкретные пины
и проверяется, но остаётся **закладкой** (`connections` в результате функции) — провод пишет
расстановщик через `applyConnections(nodes, connections)`. Сам генератор ноды не двигает
(`NodePosX/NodePosY = 0`) и не соединяет (ни одного `LinkedTo`); knot'ы, комментарии и
выравнивание пинов — не его задача. `verifyStage1()` сверяет текст с моделью (ноды, пины,
нулевые координаты, отсутствие связей) и ловит потерю кода при сериализации.
Эталонный тест с критериями: `tests/three-stage-01.sequence.md`.

## 2. Расстановщик — `src/arranger.js`

`arrangeRows(rows, { x, y, gap, rowGap })` размещает переданные явно ряды: внутри ряда слева направо, каждый следующий ряд ниже предыдущего. Интервал учитывает оценочную ширину ноды и `gap`. `arrangeFlow()` может вывести простой порядок из связей, но для ветвлений, data-only узлов и случаев, где порядок задаётся exec-цепочкой, передавай ряды явно.

Этот этап отвечает за базовую структуру, последовательность, переносы между рядами и создание reroute-knot узлов для exec-связей, которые идут назад или между разными рядами. `applyConnections(nodes, connections)` материализует соединения, заложенные ступенью 1 (генератор `LinkedTo` не пишет). Возвращаемый результат содержит исходные расставленные ноды, созданные knot-ноды и `levels` (границы рядов `top/bottom`).

Коридор knot-переноса считается по границам уровней, а не «под целевым рядом» (вердикт пользователя по `tests/three-stage-01.stage2-arranger.txt`): `rerouteCorridorY(source, target, levels)` берёт середину между самым низким низом уровней от уровня источника до уровня, предшествующего цели, и верхом целевого уровня; для обратного (upward) переноса — зеркально. Результат привязывается к сетке `GRID`. X knot'ов остаются «правый край источника + `KNOT_SIDE_OFFSET`» и «левый край цели − `KNOT_SIDE_OFFSET`» — по X самих пинов knot'ы выставит ступень 3. Точная геометрия пинов на этом этапе ещё не корректируется. Правило «knot'ы в щели между уровнями, а не под целевым рядом» проверяется отдельно: `node tools/check-knot-corridor.mjs` (входит в `npm test`) — он читает текст ступени 2, восстанавливает уровни по Y реальных нод и требует, чтобы Y каждой пары knot'ов лежал в коридоре между уровнем источника и уровнем цели.

## 3. Декоратор — `src/decorator.js`

Правило ТЗ: «берёт XY пинов соединённых нод, двигает ноды так, чтобы Y подходящих пинов
совпадали, и оставляет зазор в 5 шагов сетки по X; knot-переносы: X первого = X пина-выхода
первой не-knot ноды, X второго = X пина-входа второй, Y обоих — посередине между низом верхней
строки и верхом нижней». Реализация (2026-09-27) состоит из четырёх проходов и ничего, кроме
координат, не меняет:

1. **exec-скелет уровня.** `groupByRowY(real)` даёт строки черновика; внутри строки обход идёт от
   ядра (событие или вход, приехавший через knot-перенос) по exec-связям. Следующий узел:
   `x = max(курсор строки, правый край водителя) + clearance`, `y += pinY(водитель.выход) −
   pinY(узел.вход)`. Отсюда «лесенка» ряда до ±32px — цена прямой проводки.
2. **Данные.** Двигаются только «чистые» ноды данных (без exec-пинов): геттеры, литералы, чистые
   функции. Лестница вариантов: Y+X → только X → только Y → не трогать, с записью причины в
   `notes`. Узел с exec-пинами остаётся там, где его поставил ряд/шаблон.
3. **Щели между уровнями.** Если выравнивание съело межуровневый зазор, ряд (и всё под ним)
   сдвигается вниз на `minLevelGap = 2 * grid` — порядок и состав уровней не меняются.
4. **Knot-переносы.** `flatLinks()` раскрывает цепочки knot'ов и даёт связи «нода → нода» с
   `via`. Тогда `knot1.x = pinCenterX(источник.выход)`, `knot2.x = pinCenterX(цель.вход) − KNOT_W`
   (шина knot'а — одна клетка 16, InputPin слева, OutputPin справа), Y = `rerouteCorridorY` по
   границам уровней ПОСЛЕ выравнивания. Создавать и удалять переносы ступень 3 не вправе.

`clearance` по умолчанию = `5 * grid` (80 при grid 16) — это и есть «5 шагов сетки». Привязка к
сетке по умолчанию выключена (`snap: false`): округление ломает совмещение пинов, а совмещение —
критерий ступени. Модель пина (`pinCenterY`/`estNodeWidth`) общая со ступенями 1—2, её всё ещё
надо сверять copy-back'ом из UE.

Критерии закреплены тестом: `node tools/check-decoration.mjs [код-на-входе] [код-на-выходе]`
(входит в `npm test`) — совмещение пинов, зазор, knot'ы по пинам в коридоре, отсутствие наложений
и сдвинутых ядер уровней.

Координаты pin centers по умолчанию оцениваются моделью высоты заголовка и строк пинов. Для калибровки можно передать `pinY(node, pin)` с измерениями из Unreal Editor. Оценка ширины нод также модельная — её нужно сверять в UE.

## Объединённый вызов

`src/layout-pipeline.js` экспортирует `positionBlueprint()` — вызов расстановщика, затем декоратора. Создание нод и связей выполняется заранее. Старые layout-функции в `generator.js` оставлены для совместимости существующих скриптов; для новых генераторов используй отдельные stage-модули.

STRICT и unit-тесты проверяют структуру и расчёты модели, но не подтверждают UE-вставку, компиляцию или фактическое расположение пинов в редакторе.
